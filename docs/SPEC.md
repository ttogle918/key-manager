## 1. 프로젝트 개요

### 1.1 한 줄 정의
스크린샷이나 URL을 던지면 **"이건 Notion API 키, 이건 database ID, 이건 data source ID"처럼 맥락으로 정체를 가려** 공식 환경변수명에 매핑하고, 로컬에 암호화해 나만 볼 수 있게 보관하는 **개인 개발자용 자격증명 관리 도구**.

### 1.2 배경 & 문제 정의
개발자와 노코드 빌더는 API 연동 과정에서 키·토큰·ID를 끊임없이 발급받는다. 이것들은 보통 메모장이나 이름 없는 텍스트 파일에 흩어져 저장되며, 두 가지 고통을 낳는다.

1. **"이게 무슨 키인지 모른다."** 특히 같은 형식의 값이 여러 종류로 존재하는 서비스가 문제다. 예: 노션의 `database_id`·`data_source_id`·`page_id`는 **전부 동일한 32자리 UUID**라 값만 봐서는 구분이 불가능하다. 카카오는 REST/JavaScript/Admin/Native 키가 한 화면에 비슷한 모습으로 나열된다. GCP는 API 키·서비스 계정 JSON·OAuth 클라이언트가 뒤섞인다.
2. **"안전하게 보관할 곳이 없다."** 평문 메모는 유출에 취약하고, 정작 필요할 때 어떤 값이 무엇이었는지 다시 헷갈린다.

### 1.3 목표 & 범위
- **목표**: 흩어진 자격증명을 "던지면 → 정체를 가려 → 공식 변수명으로 정리 → 암호화 보관 → 한눈에 조회"하는 단일 흐름으로 만든다.
- **MVP 범위**: 입력(스크린샷·URL·텍스트) / 2단 분류(값 기반 + 맥락 기반) / 서비스 지식베이스(4종) / 변수명 매핑 / 암호화 저장·인증 / 조회 대시보드.
- **비(非)범위 (스코프 사수)**: 런타임 자동 주입(dotenv/EnvKey 영역), 팀 공유·동기화, 클라우드 서버. — 개인·로컬·분류에 집중한다.

## 2. 기존 솔루션 분석 & 차별점

### 2.1 기존 도구 분류
| 분류 | 대표 | 하는 일 | 한계 |
|---|---|---|---|
| 값 기반 식별기 | SecurityWall, TruffleHog, Gitleaks | 키 문자열을 정규식으로 매칭해 "이건 OpenAI 키" 식별·검증 | **generic 포맷(UUID 등)에서 후보 다중 매칭 → 구분 불가** |
| 시크릿 매니저 | Vaultwarden, Infisical, Doppler | 암호화 저장·팀 배포·런타임 주입 | 자동 분류 없음, 서비스 내부 ID 의미 이해 못 함, 기업/팀 중심·무거움 |
| NHI 인벤토리 | Entro, GitGuardian | 조직 전반의 자격증명 발견·거버넌스 | 보안팀용·고가, 개인 개발 경험(DX) 무관 |

### 2.2 공통 한계
- **값만으론 애매한 키를 구분하지 못한다.** 기존 식별기가 정확히 이 지점에서 "여러 후보 가능"이라며 손든다.
- **기업·팀·보안팀 중심**이라, "개인 개발자가 헷갈리는 키 더미를 정리"하는 DX는 누구도 풀지 않는다.

### 2.3 본 프로젝트의 차별점
1. **맥락 기반 분류**: 값이 아니라 **출처(스크린샷의 라벨, URL 구조)**를 신호로 써서 동일 형식 값을 구분한다. 기존 도구의 사각지대.
2. **개인·로컬 우선**: 서버 없이 내 기기에서만 동작·저장. "나만 보기"에 부합하고 유출면이 작다.
3. **확장 가능한 지식베이스**: 서비스 정의를 데이터(YAML)로 분리해 커뮤니티가 PR로 새 서비스를 추가 → 오픈소스로서 성장 구조.

## 3. 솔루션 개요 & 핵심 시나리오

### 3.1 핵심 사용자 흐름
1. 노션 통합 설정 화면을 **스크린샷**으로 캡처해 앱에 붙여넣는다.
2. 앱이 OCR로 값과 **라벨**을 읽고, 지식베이스와 대조해 "Secret = Notion API 키", "URL 속 UUID = database_id"로 **분류**한다.
3. 각 값을 **공식 변수명**(`NOTION_API_KEY`, `NOTION_DATABASE_ID`)에 매핑해 보여주고, 사용자가 확인·확정한다.
4. 마스터 비밀번호로 **암호화 저장**한다.
5. 이후엔 **인증 후** 대시보드에서 서비스별로 한눈에 조회·복사한다.

### 3.2 Magic moment (데모의 핵심)
"여러 키가 뒤섞인 어지러운 콘솔 화면을 통째로 던졌더니, **라벨이 붙은 깔끔한 key–value 목록**으로 정리된다." — 3분 시연영상의 첫 30초에 배치.

## 4. 기능 명세 (상세)

> 각 기능은 **설명 / 입력·출력 / 처리 / 수용 기준(AC)** 으로 기술한다. 결과 칸은 빌드 후 채운다.

### 4.1 입력 수집
- **설명**: 스크린샷(1순위), URL(보조), 텍스트 붙여넣기(기본) 세 경로로 자격증명을 받는다.
- **입력·출력**: 이미지/URL/문자열 → 정규화된 분류 요청.
- **처리**: 이미지는 4.2 OCR로, URL은 맥락 분류로, 텍스트는 값 기반 분류로 라우팅.
- **AC**: ① 스크린샷 붙여넣기 수 초 내 결과 카드 표시 ② 빈/깨진 입력에도 크래시 없음.

### 4.2 분류 엔진 — Stage 1 (값 기반)
- **설명**: 접두사가 명확한 키를 정규식으로 즉시 식별.
- **처리**: `sk-`(OpenAI), `ghp_`(GitHub), `AKIA`(AWS), `AIza`(Google), `xoxb-`(Slack) 등 + 엔트로피 보조 판정. Gitleaks(MIT) 패턴 참고분은 출처 기록.
- **AC**: 10종 더미 키 정확 매핑, 미상 값은 "unknown"으로 안전 분류(오식별 금지).

### 4.3 분류 엔진 — Stage 2 (맥락 기반) ★ 차별점
- **설명**: 값만으론 모르는 키를 라벨·URL 맥락으로 가려낸다.
- **처리**:
  - **라벨 신호**: OCR로 추출한 값 주변 텍스트("Database ID", "Internal Integration Secret", "REST API 키")를 지식베이스 라벨 사전과 대조.
  - **URL 신호**: 입력 URL을 서비스 URL 패턴과 대조(예: `notion.so/{ws}/{database_id}?v=…`에서 위치로 database_id 도출).
  - **가중 합산** → confidence. 라벨·URL이 충돌하면 단정하지 않고 "확인 필요" 표시.
- **AC**: 노션 DB URL 속 UUID를 page_id와 구분, 카카오 4종 키를 라벨로 각각 분류, 충돌 시 임의 단정 안 함.

### 4.4 서비스 지식베이스
- **설명**: 서비스별 키 종류·라벨·URL·공식 변수명을 **데이터(YAML)**로 선언.
- **스키마**: `service, credentials:[{kind, label_patterns, url_patterns, value_regex?, official_env_name, expiry_known}]`.
- **초기 4종**: Notion / Kakao / GCP / OpenAI.
- **AC**: 새 서비스 YAML 한 개 추가만으로 분류 대상에 포함(코드 수정 0).

### 4.5 변수명 매핑
- **설명**: 분류 결과를 표준 환경변수명으로 변환(`NOTION_DATABASE_ID` 등).
- **AC**: 동일 서비스 다종 키가 각기 다른 official_name으로 정확 매핑.

### 4.6 암호화 저장 & 인증
- **설명**: 마스터 비밀번호 기반으로 값을 암호화 저장하고, 조회 시 인증을 요구.
- **AC**: 저장·로드 라운드트립 복원 / 틀린 비밀번호는 복호화 거부 / SQLite 직접 열람 시 평문 미노출 / 잠금 상태 값 마스킹. (상세는 6장)

### 4.7 조회 대시보드
- **설명**: 서비스별 그룹으로 묶어 한눈에 보여주고, 인증 후 값 복사·편집·삭제.
- **AC**: 같은 서비스 키 그룹화 / 잠금 시 마스킹 / 삭제는 확인 다이얼로그.

### 4.8 (확장, stretch) 신뢰 기능
- **유효성 체크**: 사용자가 명시 실행 시 read-only 엔드포인트로 1회 호출해 `active/invalid/unknown` 표시(자동 주기 호출 안 함).
- **만료 관리**: 만료일 수동 입력(JWT는 exp 자동 파싱), 임박 뱃지.
- **`.env` 내보내기**: 인증 후 표준 변수명으로 내보내기(평문 노출 경고).

## 5. 시스템 아키텍처

### 5.1 전체 구성 (로컬 우선)
```
[ React + TS 프론트엔드 ]  ←→  [ FastAPI 로컬 백엔드 ]
                                   ├─ OCR (Tesseract/PaddleOCR)
                                   ├─ 분류 엔진 (Stage1 정규식 / Stage2 맥락)
                                   ├─ 지식베이스 로더 (YAML)
                                   ├─ 암호화 (cryptography: Argon2id + AES-256-GCM)
                                   └─ 저장소 (SQLite, 암호문만)
※ 외부 서버·클라우드 없음. 모든 데이터는 사용자 기기에만 존재.
```

### 5.2 분류 파이프라인 데이터 흐름
입력 → (이미지면) OCR로 text+label+bbox 추출 → Stage1 값 기반 1차 판정 → unknown/ambiguous만 Stage2(라벨·URL 맥락) → 변수명 매핑 → 사용자 확정 → 암호화 저장.

### 5.3 기술 스택 (전부 permissive 라이선스)
| 영역 | 선택 | 라이선스 |
|---|---|---|
| 백엔드 | FastAPI | MIT |
| 프론트 | React + TypeScript | MIT |
| 저장소 | SQLite | Public Domain |
| OCR | Tesseract / PaddleOCR | Apache-2.0 |
| 암호화 | cryptography | BSD/Apache-2.0 |
| 정규식 참고 | Gitleaks 패턴 | MIT (출처 표기) |

> ⚠️ TruffleHog(AGPL-3.0) 코드·패턴은 사용하지 않는다 — MIT와 충돌.

## 6. 보안 설계 ★

### 6.1 위협 모델
- **보호 대상**: 저장된 자격증명의 기밀성.
- **방어 범위**: 분실·도난된 기기의 디스크 접근, 우발적 파일 유출, 어깨너머 훔쳐보기, 저장소 파일 직접 열람.
- **방어 범위 밖(한계로 명시)**: 이미 장악된 호스트(키로거·메모리 덤프), 사용자의 약한 마스터 비밀번호. — 보고서 "한계" 절에 정직하게 기술.

### 6.2 암호화 설계
- **키 유도(KDF)**: 마스터 비밀번호 → **Argon2id**로 암호화 키 유도. 솔트는 저장(공개 가능), **유도된 키는 메모리에만** 두고 잠금 시 폐기.
- **암호화**: 항목별 **AES-256-GCM**(인증 암호화), 매 암호화마다 **고유 nonce**. 무결성 태그로 변조·오(誤)복호 탐지.
- **저장**: SQLite에는 **암호문·nonce·메타데이터만** 저장. **평문 값 컬럼 없음.**
- **비밀번호 변경**: 재암호화 경로 제공.

### 6.3 로컬 우선 = 공격면 최소화
서버·네트워크 전송이 없으므로 원격 유출·서버 침해 벡터가 원천 차단된다. "나만 보기" 요구와 정확히 일치.

### 6.4 접근 통제
- 조회·복사·내보내기 전 마스터 비밀번호 인증.
- 일정 시간 후 **자동 잠금**, 잠금 상태에선 메타데이터만 노출·값 마스킹.
- 인증 연속 실패 시 지연.

### 6.5 도구 자체의 시크릿 위생
- **실제 키를 저장소(git)에 절대 커밋하지 않음** — 예시·테스트는 더미만 사용.
- 클립보드 복사 시 짧은 시간 후 자동 비우기(선택), 화면 마스킹 기본.

## 9. 기대 효과 & 활용 방안
- **개인 개발자/노코드 빌더**: 흩어진 키를 정리·식별하는 시간 절약, 평문 메모 대체.
- **온보딩**: "이 UUID가 뭔지" 헤매는 노션·카카오·GCP 연동 초기 비용 감소.
- **오픈소스 자산**: 지식베이스가 커질수록 가치가 누적되는 커뮤니티형 도구.

## 10. 한계 & 향후 계획
- **한계**: 분류 정확도는 지식베이스 큐레이션 품질에 의존(서비스 콘솔 개편 시 갱신 필요). 장악된 호스트는 방어 범위 밖. 마스터 비밀번호 강도에 보안이 종속.
- **향후**: 런타임 주입(SDK), 더 많은 서비스, 브라우저 확장.

### 10.1 향후 비전 — DOM 기반 자동 캡처 (의도적 후행 과제)
스크린샷 OCR보다 정확한 경로로, 브라우저 확장이 자격증명 콘솔 페이지의 **DOM에서 라벨과 값을 직접 읽어** 분류하는 방향이 있다. 마스킹·저해상도로 OCR이 깨지는 경우를 피하고, "발급 순간 페이지에서 값을 바로 포착"하는 더 강한 비전으로 이어진다.

다만 본 프로젝트는 **보안 도구**이므로, 이 자동화는 MVP에 포함하지 않고 **의도적으로 후행 과제로 둔다.** 화면·브라우저에 대한 에이전트 권한, 자동 클립보드·캡처 접근은 그 자체로 새로운 공격면이자 프라이버시 위험이며, "로컬 우선·서버리스로 공격면을 최소화한다"는 본 도구의 설계 원칙과 충돌할 수 있다. 따라서 현재는 **사용자가 능동적으로 스크린샷/URL을 제공하는 안전한 입력 방식**을 채택하고, DOM 기반 자동 캡처는 권한 모델·프라이버시 설계·사용자 동의 흐름을 충분히 검증한 뒤 도입한다. (※ 서드파티 브라우저 에이전트를 경유하더라도, 도구 제공자의 약관은 통상 책임을 개발자·운영자에게 귀속시키므로, 안전 책임은 본 프로젝트 설계에 있다고 전제한다.)
