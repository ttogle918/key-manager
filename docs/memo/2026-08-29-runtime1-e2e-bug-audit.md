# 버그 감사 메모 — keylens-env 엔드투엔드 점검 (2026-08-29)

> 대상: **키 등록 → 패키지 설치 → 다른 레포에서 키 가져오기** 전 구간(RUNTIME-1).
> 계기: 이 SDK를 실제 다른 레포에서 쓰기 시작하기 전에 한 번 훑어보자는 요청.
> 방법: 문서 검토가 아니라 **실제로 돌려서** 확인했다 — 임시 금고로 백엔드를 띄우고,
> 별도 venv에 `pip install` 한 뒤(로컬 경로 + README의 `git+https` 경로 둘 다),
> `.keylens.toml`을 만들고 `load_env()`를 호출해 승인·수신까지 재현했다.
> 결과: 행복 경로는 정상. 기존 테스트 330개도 전부 통과. **그 바깥에서 9건**이 나왔다.

## 1. cp949 콘솔에서 에러 메시지가 크래시난다

**증상**: 모든 SDK 에러 메시지에 em dash(U+2014)가 들어 있었는데 cp949에 그 문자가
없다. 한글 Windows 콘솔의 기본 `sys.stdout.encoding`은 cp949이고, 그 에러 핸들러
(`surrogateescape`)로는 U+2014를 넘길 수 없다.

```
KeylensApprovalPendingError: '...'가 'blog' 프로젝트 키를 요청했어요 — ...
UnicodeEncodeError: 'cp949' codec can't encode character '—'
```

**왜 심각한가**: README가 권장하는 그대로 `except KeylensEnvError as e: print(e)` 를 쓰면
죽는다. 그리고 하필 **신규 사용자가 가장 먼저 만나는 에러**가 승인 대기 에러다. 즉
"처음 써 보는 사람이 가장 높은 확률로 만나는 경로"가 정확히 이 크래시였다.
(이 메모를 쓰는 도중 작업용 스크립트도 같은 이유로 한 번 죽었다.)

**수정**: 사용자에게 보이는 메시지의 em dash를 ASCII 하이픈으로 교체. 문자 하나 고치고
끝낼 문제가 아니라 규칙이 필요해서, `tests/test_messages.py` 가 소스의 **모든 메시지
문자열**을 AST로 훑어 cp949 인코딩 가능 여부를 검사한다(독스트링은 제외 — 사용자에게
출력되지 않고, 레포의 한국어 서술 스타일을 굳이 깨고 싶지 않았다).
CLI(`__main__.py`)는 한 겹 더: `_print()`가 콘솔 인코딩으로 먼저 인코딩해 보고
불가 문자는 대체 문자로 바꾼다.

**남은 것**: 백엔드 메시지에도 em dash가 30군데 있다. 그쪽은 HTTP JSON으로 브라우저
UI에만 나가고(브라우저는 UTF-8), SDK는 자기 메시지를 따로 만들기 때문에 콘솔 크래시
경로가 아니다 — 그래서 건드리지 않았다.

## 2. 프로젝트 미지정 키가 SDK로 안 온다

**증상**: `POST /vault/entries` 에서 `project`를 비우면 백엔드가 **오늘 날짜**를 넣는다
(`main.py` `vault_add`). 그래서:

```
{"official_name":"NOTION_TOKEN", ...}  ->  project: "2026-08-29"
```

`sdk_repo.entries_for_env`의 "전역 키"(`project IS NULL OR project = ''`) 분기는
**일반 API로는 도달할 수 없다** — 번들 import 로만 그런 행이 생긴다. 결과적으로
프로젝트를 안 고르고 저장한 키는 날짜 이름의 가짜 컬렉션이 되고, `load_env("blog")`로
영영 오지 않는다. 오류도, 경고도 없다.

**수정 판단**: 날짜 기본값 **자체는 그대로 뒀다**. 프론트가 이 값에 의존한다
(`keylensStore.ts`의 `findDup`가 `v.project === v.addedAt` 으로 "미지정 항목"을 판별하고,
금고 화면의 등록일 그룹핑도 같은 값을 쓴다). 그리고 이걸 `NULL`(=전역)로 바꾸면 오히려
**아무 생각 없이 저장한 키가 모든 컬렉션에 딸려 나가는** 더 나쁜 동작이 된다.

대신 **조용한 실패를 없애는 쪽**으로 고쳤다:

- `load_env()`가 주입할 변수 0개면 `KeylensEmptyCollectionError`를 던진다. 예전에는
  빈 dict를 조용히 주입하고 성공한 척해서, 한참 뒤 엉뚱한 자리에서 `KeyError`로 터졌다.
  메시지에 "프로젝트를 지정하지 않고 저장한 키는 등록일 이름으로 묶인다"는 원인을 적었다.
- `collections()` / `keylens-env collections` 로 날짜 이름 컬렉션이 눈에 보이게 했다.

**남은 것(후속 후보)**: 프론트 저장 화면에서 프로젝트를 비우고 저장할 때 "이 키는
`2026-08-29` 컬렉션으로 들어가고 `load_env`로는 오지 않는다"고 알려주는 게 근본 해결에
가깝다. 프론트 변경이라 이번 범위에서는 뺐다.

## 3. 자동잠금이 SDK 사용으로 갱신되지 않는다

**실측**(`KEYLENS_AUTOLOCK_SECONDS=8`, 계속 호출하면서):

```
t=0s [200]   t=4s [200]   t=8s [401]   t=12s [401]
```

`vault_session.sdk_env`가 의도적으로 `_require_key(refresh=False)`를 쓴다. **설계 의도는
타당하다** — 자리를 비운 사용자를 보호하려는 것이고, SDK 조회로 타이머가 갱신되면
스크립트가 도는 동안 금고가 사실상 영원히 열려 있게 된다.

**문제는 문서였다**: 기본값이 300초인데 `keylens-env/README.md`에
`KEYLENS_AUTOLOCK_SECONDS` 언급이 아예 없었다. UI를 안 만지면 5분마다 마스터 비밀번호를
다시 넣어야 스크립트가 도는데, 그 사실을 알 방법이 없었다.

**수정**: README에 "자동 잠금 주의" 절 추가 + `KeylensLockedError` 메시지 자체에
"무활동 5분이면 자동으로 잠깁니다. KEYLENS_AUTOLOCK_SECONDS로 조정할 수 있어요"를 넣었다.
동작은 그대로 뒀다.

## 4. 원시 예외가 KeylensEnvError 밖으로 샌다

`exceptions.py` 독스트링은 "실패는 항상 이 계층의 예외로 표면화된다"고 약속하는데,
두 군데가 그걸 어겼다:

```
BUG - KeylensEnvError 밖의 예외가 샌다: JSONDecodeError   # 응답이 JSON이 아님
BUG - 새는 예외: KeyError : 'values'                      # JSON이지만 형식이 다름
```

**현실적인 방아쇠**: 기본 주소 `127.0.0.1:8765`에 KeyLens가 아닌 **다른 프로그램**이
떠 있는 경우. 8765는 흔한 포트다(점검 중 8899에서도 다른 서버를 만났다).

**수정**: `client._request`가 파싱·형식 실패를 전부 `KeylensServerError`로 정규화하고,
메시지에 "그 포트를 다른 프로그램이 쓰고 있는지 확인하세요"를 넣었다. 더불어 `/health`로
**KeyLens가 맞는지 먼저 확인**하고 붙게 바꿔서(아래 참고) 애초에 남의 앱에 POST하지 않는다.

## 5. 메모장 저장 인코딩

`config.py`가 `read_text(encoding="utf-8")` 고정이라:

- UTF-8 **BOM**(메모장 'UTF-8') → `KeylensConfigError: 올바른 TOML 형식이 아니에요`
  (원인이 BOM이란 걸 알 수 없는 메시지)
- **UTF-16**(메모장 '유니코드') → 원시 `UnicodeDecodeError` (4번과 같은 계약 위반)

**수정**: `utf-8-sig`로 읽고(BOM 있으면 떼고, 없으면 utf-8과 동일), `UnicodeDecodeError`는
"메모장의 '유니코드'(UTF-16) 대신 'UTF-8'로 다시 저장하세요"라는 `KeylensConfigError`로 변환.

## 6. 기존 환경변수를 무조건 덮어쓴다

`os.environ.update(values)` — python-dotenv는 기본이 `override=False`인데 반대였고,
끌 방법도 없었다. 셸이나 CI에서 export한 값이 조용히 사라진다.

**수정**: `load_env(..., override=True)` 파라미터 추가. **기본값은 True로 유지**했다 —
기존 동작을 말없이 바꾸면 이미 이 패키지를 쓰는 코드가 조용히 다르게 동작하게 되고,
"금고가 단일 진실 공급원"이라는 이 도구의 전제와도 맞는다. 필요하면 `override=False`.
`load_env()`가 실제로 주입한 `{이름: 값}`을 반환하도록도 바꿨다(무엇이 들어갔는지 확인용).

## 7. 동시 요청 시 500

미승인 경로로 20개 병렬 요청 → `403 x19, 500 x1`:

```
sqlite3.IntegrityError: UNIQUE constraint failed: sdk_pending_requests.project, ...path_norm
```

`sdk_repo.add_pending_request` / `add_project_dir`가 SELECT로 존재를 확인한 뒤 INSERT 하는
2단계라, 동시에 들어오면 둘 다 "없음"을 보고 INSERT 한다. 여러 스크립트를 동시에 돌리는 건
실제로 일어나는 일이다.

**수정**: `INSERT ... ON CONFLICT(project, path_norm) DO NOTHING` 한 문장으로 바꾸고,
충돌로 아무 행도 안 들어갔으면 기존 행 id를 읽어 반환한다.
**회귀 테스트가 실제로 옛 버그를 잡는지 확인함** — 12스레드 배리어로 동시 진입시켰을 때
옛 구현은 11건 `IntegrityError`, 새 구현은 0건.

## 8. [보안] 승인 게이트를 로컬 프로세스가 스스로 우회

**재현**:

```
1) POST /sdk/env {path:"/evil/dir"}      -> 401 (잠김)
2) POST /sdk/projects/blog/directories   -> 200  <- 잠긴 상태에서도, 인증 없이 통과!
3) (사용자가 잠금 해제)
4) POST /sdk/env {path:"/evil/dir"}      -> 200 {"OPENAI_API_KEY":"sk-..."}

대안 경로: POST /sdk/pending/{id}/approve -> 200  (자기 요청을 자기가 승인)
```

**맥락**: `keylens-env/README.md`의 "보안 프레이밍" 절은 *"이 SDK가 새로운 신뢰 경계를
만드는 건 아니다 — 잠금 해제 상태에선 이미 로컬 프로세스가 vault API를 호출할 수 있었다"*
고 정직하게 밝히고 있고, 그건 사실이다(`GET /vault/entries/{id}/value`도 무인증).
그래서 이건 "새로 뚫린 구멍"은 아니다.

**그래도 고친 이유**: 같은 문단의 **"승인된 프로젝트 것만 내려주는 최소 권한 스코핑"**
이라는 주장이 성립하지 않았다. 스코핑을 대상이 스스로 부여할 수 있으면 스코핑이 아니다.
그리고 "승인 대기" UI는 사용자에게 **없는 보호를 있는 것처럼** 보여준다.
`SECURITY.md`도 "인증 게이트 우회"를 명시적으로 범위 안에 두고 있다.
(`SECURITY_REVIEW.md`는 `crypto.py`가 없던 시점 문서라 이 표면을 다루지 않는다.)

**수정 원칙 — 권한의 *방향*으로 나눈다**:

- **넓히는 쪽**(디렉토리 등록 `add_project_dir`, 대기 승인 `approve_pending`)
  → 잠금 해제 필수. 다루는 데이터가 문자열이냐가 아니라 **권한 부여냐**가 기준이다.
- **좁히는 쪽**(등록 해제, 거부)과 단순 조회 → 잠긴 상태에서도 허용(안전한 방향).

프론트도 이 두 액션에서 401을 받으면 잠금 상태를 UI에 반영하도록 고쳤다.

**여전히 남는 것**: 잠금 해제 상태에서 로컬 프로세스가 `/vault/entries/{id}/value`로
값을 직접 읽는 경로는 그대로다(기존 위협 모델대로 범위 밖). 이번 수정은 "승인 게이트가
게이트 역할을 하게" 만든 것이지, 로컬 무인증 API 전체를 닫은 게 아니다.

## 9. 승인 대기 뱃지가 자동 갱신되지 않음

프론트 전체에 `setInterval`이 0개였다. `loadPending()`은 부팅·화면 진입·승인 직후에만
호출된다. SDK 요청은 **앱 밖(다른 터미널)에서** 오므로, 앱을 켜 둔 채로 스크립트를 돌리면
사이드바 뱃지가 영영 0으로 남는다. 데스크톱 exe는 OS 알림 훅(`desktop/app.py`의
`set_pending_hook`)이 있어 덜하지만, **dev 모드(브라우저)는 알림도 폴링도 없어서** 요청이
온 걸 알 방법이 아예 없었다.

**수정**: 5초 주기 폴링(`startPendingPoll`) 추가, `cleanup()`에서 정지, 중복 기동 방지.

## 확인했지만 문제 없던 것

기록해 둔다 — 다음에 같은 곳을 다시 파지 않도록.

- **포트 분리**(exe 8765 / dev 8003)는 의도된 설계이고 문서화돼 있었다. 다만 매번
  `KEYLENS_BASE_URL`을 설정해야 하는 게 불편해서 **자동 탐색**으로 바꿨다(아래 참고).
- README의 `git+https://...#subdirectory=keylens-env` 설치 경로는 실제로 동작한다.
  `v0.2.0` 태그에 `keylens-env/`가 존재하는 것도 확인(`v0.1.x`에는 없다).
- **한글 프로젝트명**은 프론트·백엔드·SDK 전 구간 정상. 프론트는 `encodeURIComponent`로
  URL 인코딩하고, SDK는 JSON 본문으로 보내서 문제가 없다.
- 경로 정규화(대소문자·트레일링 슬래시 흡수)는 Windows에서 의도대로 동작.
- `sdk_fetch` 감사 로그가 실제로 내려준 항목에만 정확히 남는다.
- **잠금 상태에서 값이 새는 경로는 찾지 못했다.**
- `load_env(collection=...)`를 명시하면 실행 디렉토리마다 승인이 필요한 건 **버그가 아니라
  설계**(승인 단위가 cwd)다. 다만 하위 폴더에서 실행하면 새 승인 요청이 생기므로
  README에 `.keylens.toml` 방식을 권장한다고 명시했다.

## 곁들여 추가한 것

버그는 아니지만 이번에 같이 넣은 것:

- **컬렉션 목록 조회**: `keylens_env.collections()` + `keylens-env collections` CLI
  (`python -m keylens_env collections`와 동일). 값은 절대 출력하지 않고 이름·개수만 —
  터미널 스크롤백이나 화면 공유에 시크릿이 남지 않도록. 2번 버그의 "무엇이 있는지 모른다"를
  푸는 도구이기도 하다. `keylens-env where`로 어느 주소·컬렉션에 붙는지 진단도 가능.
- **포트 자동 탐색**: `KEYLENS_BASE_URL`이 없으면 8765 → 8003 순으로 `/health`를 찔러
  **KeyLens가 맞는 첫 주소**에 붙는다(응답 형태로 판별하므로 남의 앱을 잡지 않는다).
  환경변수가 있으면 탐색하지 않고 그 값을 그대로 쓴다 — 사용자가 명시한 주소를 말없이
  다른 포트로 바꿔치기하면 안 되므로.
- **용어 통일: "컬렉션"** — 아래 별도 절 참고.

## 용어 결정 — 키 묶음은 "컬렉션"(2026-08-29)

**결정**: 사용자에게 **보이는 모든 곳**에서 키 묶음을 **컬렉션(collection)**이라 부른다.
**코드 식별자·백엔드 API 필드·DB 컬럼은 `project` 그대로 둔다.**

| 층 | 이름 | 이유 |
|---|---|---|
| 앱 UI 문자열, 문서, SDK 공개 API·CLI, `.keylens.toml` | **컬렉션** | 사용자가 읽는 것 |
| 프론트·백엔드 코드 식별자(`project`, `sdkProjects`, `ProjectAccessScreen`) | `project` | 내부 이름, 바꿀 이득 대비 회귀 위험 |
| HTTP 필드명·엔드포인트 경로(`/sdk/projects`, `{"project": ...}`) | `project` | **아래 참고 — 절대 바꾸면 안 됨** |
| DB 컬럼(`entries.project`, `sdk_project_dirs.project`) | `project` | 실제 금고 파일 마이그레이션 회피 |

### 왜 "프로젝트"가 아니라 "컬렉션"인가

이 시스템에는 서로 다른 두 개가 있고 **1:N**이다:

1. 키 묶음 — `blog`
2. 그 묶음을 쓸 수 있는 **허용 디렉토리 목록** — `C:epolog`, `C:epolog-admin`, ...

그런데 예전에는 **1번을 "프로젝트"라고 불렀다.** 사람들이 실제로 "프로젝트"라고 생각하는 건
2번(레포 디렉토리)인데도. 그래서 "프로젝트 접근" 화면이 "프로젝트를 고르면 그 안에 디렉토리
목록이 있다"는 묘한 구조로 읽혔다. 컬렉션으로 바꾸면 문장이 그냥 풀린다:

> "**블로그 컬렉션**의 키를 **이 디렉토리들**이 쓸 수 있다"

부수 효과로 위 **2번 버그의 뿌리도 정직해진다**. `2026-08-29`는 프로젝트가 아니지만,
컬렉션(이름 붙은 통)으로는 정확히 말이 된다. 벡터스토어가 네임스페이스를 컬렉션으로
나누는 것과 같은 개념이다.

인정한 트레이드오프: 승인 단위가 디렉토리라 전체 경험이 레포 모양이고, 비개발자에게는
"컬렉션"이 "프로젝트"보다 낯선 단어다. 위의 1:N 구조가 더 무겁다고 판단했다.

### 왜 와이어 포맷과 DB는 바꾸지 않는가

**`keylens-env`는 다른 레포에 pip으로 설치되고 버전이 고정된다.** `/sdk/env`의 요청 필드를
`project` → `collection`으로 바꾸면:

```
어느 레포에 keylens-env 0.2.0이 고정돼 있음 + 앱만 업데이트 → 422 Validation Error
```

버전 스큐 실패가 생긴다. 결국 백엔드가 두 필드를 모두 받아야 하고, 그러면 바꾼 의미가 없다.
DB 컬럼도 마찬가지 — 사용자 눈에 아무 차이가 없는 변경을 위해 실제 키가 든 금고 파일을
마이그레이션하는 건 순수 리스크다. **와이어·DB의 옛 이름은 정상적인 구현 세부사항이다.**

### 하위 호환

`.keylens.toml`의 `project` 키와 `load_env(project=...)`는 계속 받는다(`collection`이 우선).
이미 이 패키지를 쓰던 코드는 아무것도 고치지 않아도 된다.
