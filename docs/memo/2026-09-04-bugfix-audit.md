# 버그 수정 메모 - 배포물·초기화 경로 감사 (2026-09-04)

> 대상: **릴리스 배포물**(zip → 압축 해제 → 실행)과 **금고 초기화 경로**(비밀번호 분실 포함).
> 계기: v0.5.0 을 낸 뒤 "패키지랑 GUI 가 잘 되는지만 보면 되겠네"라는 확인에서 시작했다.
> 방법: 문서·테스트 검토가 아니라 **실제로 받아서 눌렀다** - 게시된 zip 을 새 폴더에 풀어
> 실행하고, 브라우저로 기능을 하나씩 조작하고, 잊은 비밀번호 시나리오를 그대로 재현했다.
> 결과: **6건**. 전부 백엔드 353개·프론트 75개 테스트와 CI 6종을 **통과한 상태에서** 나왔다.

## 1. [보안] 릴리스 zip 에 금고 파일이 동봉됐다

**증상**: v0.5.0 배포본을 압축 해제하니 `vault.db` 가 들어 있었다.

**원인**: 패키징된 앱은 금고를 **실행 파일 옆에** 만든다(`desktop/app.py` 의
`KEYLENS_VAULT_PATH`). 그래서 빌드한 exe 를 **한 번 실행해 보는 것만으로**(= 릴리스 전
정상적인 스모크 테스트) 산출물 안에 금고가 생기고, 그대로 압축된다.

이번엔 빈 파일이라 유출은 없었다. 그러나 키를 넣어 확인한 뒤 압축했다면 **암호화된 금고가
배포**됐을 것이다. 값은 암호문이지만 `service`·`label`·`project`·`memo` 는 평문이다.

> 열심히 확인할수록 위험해지는 구조였다. 옳은 습관(릴리스 전 스모크 테스트)이 곧 원인이다.

**수정**: `desktop/package.py` 를 추가해 빌드 → 위생 검사 → 압축을 한 번에 한다.
압축 전에 금고·SQLite 저널·`.env` 를 걷어내고, 완성된 zip 을 다시 열어 재확인한다.
내용이 들어 있거나 **열리지 않는** 금고는 지우지 않고 멈춘다 - 자동 삭제 자체가 데이터
사고이고, 앱이 실행 중이라 잠긴 금고일 수도 있다. 산출물 디렉토리는 `glob("exe.*")` 가
아니라 cx_Freeze 와 같은 규칙으로 계산한다(`build/` 에 몇 달 묵은 `exe.*-v2` 가 있었고,
그걸 집으면 옛날 앱이 조용히 배포된다).

**검증**: CI 잡 `packaging-guard-test` 10건. 그리고 `desktop/test_release_artifact.py` 로
배포물을 사용자처럼 풀어서 띄워 7가지를 확인한다(`b9a31d0`). **이 테스트가 실제로 실패할 수
있는지**를 v0.5.0 zip 에 대고 돌려 확인했다 - `test_artifact_carries_no_vault_or_secrets`
가 실패한다. 회귀 테스트는 실패할 줄 알아야 테스트다.

## 2. 금고를 만들기 전 SDK 조회가 500

**증상**: `/sdk/pending`, `/sdk/directories` 가 `no such table: sdk_pending_requests` 로 실패.

**원인**: `vault_repo.connect()` 가 스키마 생성을 `is_initialized()` 로 감쌌다. 감쌀 이유가
없었다 - `is_initialized()` 는 `meta` **테이블**이 아니라 그 안의 **행(id=1)** 을 보므로,
빈 테이블을 미리 만들어도 "아직 금고 없음" 판단은 그대로다. `init_vault()` 의
`executescript` 도 멱등이다.

**수정**: 조건을 없앴다. 그 결과 `reset_vault()` 직후(테이블만 남고 행은 빈 상태)와 한 번도
초기화된 적 없는 db 가 **같은 모양**이 된다 - `unlock()` docstring 이 이미 요구하던 통일이다.

## 3. 초기화 후에도 인증 백오프가 남아 새 비밀번호를 거부한다

**증상**: 비밀번호를 잊어 초기화한 뒤 새 비밀번호를 정했는데, **올바른 값으로도** 잠금 해제가
거부된다(`VaultRateLimited`). 새 금고에서 오타를 한 번만 내도 즉시 최대 백오프가 걸린다.

**원인**: `reset()` / `reset_forgotten()` 이 마지막에 `self.lock()` 만 불렀는데, `lock()` 은
`self._key = None` **하나만** 한다. 실패 카운터(`_fail_count`)와 백오프 만료시각
(`_locked_until`)은 그대로 남는다.

**이 기능을 쓰는 사람은 정의상 여러 번 틀린 뒤에 온다.** 그래서 이 버그는 예외 상황이 아니라
**주 경로**에서 터진다. 겨우 복구했는데 곧바로 벌을 받는다.

실측 재현:

```
틀린 시도 8회        -> _fail_count=3, 백오프 0.9s 남음
잊음 초기화          -> _fail_count=3, 백오프 0.9s   (그대로)
새 비밀번호 설정 후   -> VaultRateLimited (올바른 비밀번호인데 거부)
새 금고에서 오타 1회  -> 즉시 최대 백오프
```

**수정**: `_clear_auth_throttle()` 을 두고 **금고가 사라진 경로**(두 초기화)와 `init()` 에서
부른다. 사라진 금고에 대한 실패 이력을 새 금고에 물려줄 이유가 없다.

### 에지 케이스 - 순진한 수정이 보안 구멍을 만든다

`lock()` 에서 지우면 간단해 보이지만 **그러면 안 된다.** `/vault/lock` 은 인증이 없어서,
공격자가 추측 사이사이에 잠금을 걸어 백오프를 매번 초기화할 수 있다 - 지수 백오프가 통째로
무력화된다. `init()` 은 안전하다: 이미 초기화된 금고에서는 `init_vault` 가 거부하므로 살아
있는 금고의 백오프를 지우는 데 쓸 수 없다.

두 성질을 테스트로 고정했다 - `test_lock_does_not_clear_the_backoff`,
`test_forgotten_reset_clears_the_auth_backoff`.

## 4. 예외 메시지의 em dash 가 cp949 콘솔에서 프로세스를 죽인다

**증상**: 위 3번을 재현하는 스크립트가 `UnicodeEncodeError` 로 죽었다. 원인은 코드가 아니라
`VaultRateLimited` **메시지 자체**였다.

```
UnicodeEncodeError: 'cp949' codec can't encode character '\u2014'
```

**원인**: em dash(U+2014)가 cp949 에 없다. HTTP 응답은 UTF-8 JSON 이라 멀쩡해 보이지만, 이
문자열들은 `keylens-env` SDK·CLI 를 거쳐 **사용자의 터미널로 나가고 트레이스백에도 실린다.**
전수 검사하니 예외 인자와 `HTTPException(detail=...)` 에 **22건**이 더 있었다(백엔드·릴레이).

> 같은 부류를 2026-08-29 감사(#1)에서 SDK 쪽만 고쳤었다. 백엔드는 그때 범위 밖이었다.

**수정**: 26줄을 ASCII 하이픈으로 바꾸고, `backend/tests/test_console_safe_messages.py` 로
재발을 막는다. AST 로 **예외 인자와 `detail` 만** 골라 cp949 인코딩 가능 여부를 검사한다 -
주석·docstring 은 콘솔로 나가지 않으므로 대상이 아니다. 옛 문구를 그대로 고정하고 있던
`test_explain_api.py` 도 함께 갱신했다.

## 5. 승인 직후 "이미 허용한 디렉토리"가 늘어나지 않는다

**증상**: 승인 대기에서 "허용"을 누르면 서버에는 `source='approved'` 로 정상 등록되는데,
바로 아래 "이미 허용한 디렉토리"는 **0개 그대로**였다.

**원인**: `approvePending` 이 `loadPending()` 만 다시 부르고 `allSdkDirs` 는 갱신하지 않았다.

허용은 곧 디렉토리 등록이므로 같은 화면의 목록이 그 자리에서 늘어나야 한다. 그러지 않으면
방금 허용한 항목이 어디에도 보이지 않아 승인이 됐는지조차 알 수 없고, **이 섹션을 승인 화면에
붙인 이유**(권한을 주는 자리와 회수하는 자리를 붙여 둔다)가 정확히 무력화된다.

**수정**: 승인 후 두 목록을 함께 다시 불러온다.

> 타입도 테스트도 잡지 못하는 종류다 - 두 상태가 **각각은 맞고 함께 볼 때만** 어긋난다.
> 브라우저로 실제로 눌러보다 발견했다.

## 6. 이미 비어 있는 금고를 초기화하면 빨간 오류가 뜬다

**증상**: 잠금 화면에서 "비밀번호를 잊으셨나요?"를 눌렀는데 `초기화되지 않은 금고입니다`
(409)가 오류로 표시됐다. 다른 창에서 먼저 초기화했거나 화면이 낡았을 때 여기로 온다.

**원인**: 사용자가 원한 건 "비우고 처음부터 시작"인데 금고가 이미 비어 있다면 그 목적은
**이미 달성된 상태**다. 거기서 오류를 띄우면 아무것도 잘못하지 않았는데 막힌 것처럼 보이고,
다음에 뭘 해야 하는지도 알려주지 않는다.

**수정**: 두 초기화 경로 모두 409 를 성공처럼 다뤄 설정 화면으로 넘긴다. 백엔드는 409 를
그대로 둔다 - API 소비자에게 "이미 비어 있었다"는 유용한 정보이고, 그 해석은 클라이언트가
할 일이다.

## 배운 것

1. **배포물은 소스와 다른 물건이다.** 1·2번은 zip 을 받아서 열어봐야만 드러난다. 그래서
   `test_release_artifact.py` 를 만들었고, 그게 실제로 실패하는지까지 확인했다.
2. **회복 경로는 "그 상황에 처한 사람"으로 시험해야 한다.** 3번은 "여러 번 틀린 뒤"라는
   전제를 재현하지 않으면 절대 안 보인다. 행복 경로 테스트는 그 전제를 만들지 않는다.
3. **순진한 수정이 더 나쁠 수 있다.** 3번을 `lock()` 에서 고쳤다면 무차별 대입 방어를
   통째로 날렸을 것이다. 고칠 자리를 정할 때 "이 함수를 누가 부를 수 있나"를 먼저 봐야 한다.
4. **화면 상태는 조합에서 어긋난다.** 5번처럼 각각은 맞는 두 상태가 함께 볼 때만 틀리는
   버그는 눌러봐야 나온다.
