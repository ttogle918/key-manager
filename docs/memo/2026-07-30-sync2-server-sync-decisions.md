# 결정 메모 — SYNC-2 서버 동기화 설계 (2026-07-30)

> 대상: `docs/BACKLOG.md`의 **SYNC-2(계정 로그인 기반 서버 동기화, Supabase)**.
> 목적: 왜 이렇게 설계했는지 이유를 남겨서, 나중에(특히 착수 시점에) "그때 왜 이걸 골랐더라?"를 다시 헤매지 않게 한다.
> 이 메모는 코드가 아니라 결정 기록이다 — SYNC-2 착수 시 이 파일부터 다시 읽을 것.

> **⚠️ 2026-08-26 대체됨**: 이 문서의 Supabase 계정 로그인 설계는 이메일 발송 한도·오픈소스
> 대회 정합성 문제로 폐기됐다. 새 설계는
> `docs/superpowers/specs/2026-08-26-sync2-email-relay-design.md`(계정·DB 없는 SMTP 릴레이)를
> 참고 — 이 문서는 "왜 처음엔 Supabase를 골랐었는지"의 역사적 기록으로만 남긴다.

## 배경

기존 설계는 "로컬 우선·외부 서버 없음"(CLAUDE.md, SECURITY_REVIEW.md, RESULT_REPORT §8.5)이 핵심 원칙이었다. 그런데 로그인하면 서버에 자동 백업되고, 비회원이면 로컬에만 남는 **옵트인 서버 동기화**를 추가로 원하게 됐다. 이 문서는 그 설계 과정에서 나온 5개 결정과 각각의 이유를 기록한다.

---

## 결정 1 — Firebase 대신 Supabase

**결정**: 서버(로그인 + 암호문 저장소)로 Firebase가 아니라 Supabase를 쓴다.

**왜**:
- Supabase는 Postgres + Auth가 오픈소스 코어(Apache-2.0 계열) 위에 있고, 필요하면 **자체 호스팅으로 탈출할 수 있는 경로**가 있다. Firebase는 구글 클라우드에 완전히 종속된 프로프라이어터리 서비스라 벤더 락인이 크다.
- 이 프로젝트는 "오픈소스 개발자대회" 출품작이라 오픈소스 지향과의 정합성이 하나의 판단 기준이 됐다.
- 트레이드오프로 인정한 것: Firebase가 인지도·심사위원 친숙도 면에서는 더 높을 수 있다. 하지만 실제 구현·라이선스·철학 정합성을 더 중요하게 봤다.

**참고**: `@supabase/supabase-js`는 MIT 라이선스 — CLAUDE.md의 허용적 라이선스 규칙과 문제없이 부합.

## 결정 2 — 자동 실시간 동기화가 아니라 수동 동기화

**결정**: 로그인 상태에서도 서버 업/다운로드는 **자동·실시간이 아니라 사용자가 명시적으로 트리거**(로그인/로그아웃 시 확인창 + 세션 중 수동 버튼)한다.

**왜** (사용자 원문 근거):
- **다루는 게 API 키다.** 실시간으로 계속 서버에 흘려보내는 건, 값이 시크릿이라는 이 프로젝트의 전제와 맞지 않는다. 업로드 시점을 사용자가 통제해야 "언제 뭐가 서버에 올라갔는지"를 항상 알 수 있다.
- **강의 실습용 키는 애초에 저장할 필요가 없는 경우가 많다.** (배경: BACKLOG의 개발 동기 자체가 "교육 현장에서 실습용 키가 쌓이는 문제"였다.) 모든 키를 자동으로 서버까지 올리면 이 실습용·휘발성 키까지 무조건 클라우드에 남게 되는데, 이건 과한 기본값이다.
- **유출 우려**: 서버에 뭔가 자동으로 올라간다는 사실 자체가 심리적 거부감을 만든다. "내가 누른 순간에만 올라간다"는 게 사용자가 도구를 신뢰하게 만드는 조건이라고 판단했다.
- 결론적으로 **동기화 여부·시점은 항상 사용자 선택**으로 남겨둔다 — 이게 이 결정의 핵심이다.

**부가로 확인된 기술적 이점** (원래 이유는 아니고 곁다리 이득): 자동 실시간 동기화는 충돌 처리·백그라운드 네트워크 상태 관리 등 구현 복잡도를 크게 늘리는데, 수동 트리거는 이 복잡도가 거의 없다.

## 결정 3 — 로그인 계정과 마스터 비밀번호는 완전히 분리 (제로 널리지 유지)

**결정**: Supabase 로그인(이메일/비번 등)과 금고를 여는 마스터 비밀번호는 **서로 다른 비밀**이다. 로그인은 "내 데이터가 서버 어디에 있는지" 식별 용도일 뿐이고, 실제 복호화 열쇠는 항상 로컬 마스터 비밀번호에서만 유도된다.

**왜**:
- 기존 VAULT-1(Argon2id + AES-256-GCM)·SYNC-0(암호화 번들)이 이미 "서버는 절대 평문을 보지 않는다"는 제로 널리지 원칙 위에 서 있다. 여기서 로그인=마스터 비밀번호로 합치면, 서버가 원리상 평문에 접근할 수 있는 지점이 생겨 이 원칙이 깨진다.
- 대회 차별점(§8.5 "왜 로컬인가")과의 정합성 — 서버를 도입해도 "서버가 털려도 키는 안전하다"는 주장을 그대로 유지하려면 이 분리가 필수다.
- 인정한 비용: 사용자가 비밀번호를 두 개(로그인용 + 마스터) 기억해야 한다는 사용성 손해가 있지만, 보안 원칙을 지키는 쪽을 택했다.

## 결정 4 — 로그인 상태 리셋: 계정은 유지, 데이터만 삭제

**결정**: 로그인된 상태에서 "금고 리셋"을 누르면 로컬 DB와 서버의 암호문 데이터만 삭제하고, Supabase 계정(로그인 자체)은 유지한다. 회원 탈퇴가 아니다.

**왜**:
- 기존 리셋 기능의 주 사용처는 교육기관·공용 PC 시나리오(BACKLOG "기대효과" 참고) — 강의가 끝나면 다음 수강생을 위해 데이터만 지우면 되지, 계정까지 지우고 재가입시키는 건 과한 마찰이다.
- "리셋 = 계정 삭제"로 가면 되돌릴 수 없는 파괴적 동작이 되어 실수 시 피해가 커진다. 데이터만 지우는 편이 안전한 기본값이다.
- 계정 자체를 지우고 싶은 경우(회원 탈퇴)는 이번 설계 범위 밖으로 남겨뒀다 — 필요해지면 별도 옵션으로 추가.

---

## 결정 5 — 새 암호화 계층을 만들지 않고 SYNC-0 번들을 재사용

**결정**: 서버에 올리는 데이터 포맷은 새로 설계하지 않고, 이미 구현된 SYNC-0의 `.klvault.json` 번들(`/vault/export`/`/vault/import`)을 그대로 쓴다.

**왜**:
- 이 번들은 이미 "포맷 검증 + KDF 파라미터 + 항목별 nonce/암호문"을 캡슐화한 자기완결적 암호문이라, 서버는 이 JSON 덩어리를 그대로 보관/전달하기만 하면 된다 — 새 크립토 코드를 추가할 필요가 없다(공격 표면 최소화, 검증된 코드 재사용).
- 업로드 = 기존 export 결과를 Supabase에 저장, 다운로드 = Supabase에서 받은 값을 기존 import에 그대로 넘기는 것뿐이라 백엔드 변경이 거의 없다 — 개발 리스크가 낮다.

## 폐기 근거 — Supabase 기본 메일러 발송 한도 (2026-08-26 확인)

위 "대체됨" 배너가 말하는 **이메일 발송 한도**의 실제 수치를 남겨 둔다. 결론은 이미 났지만,
근거 없이 "한도 때문에 접었다"만 남으면 나중에 같은 조사를 다시 하게 된다.

**확인한 것**: Supabase 기본(커스텀 SMTP 미설정) 메일러는 가입 확인·비밀번호 재설정 메일을
**시간당 2통**으로 제한한다. 공식 문서 문구는 "2 emails per hour, Limited By: Sum of combined
requests project-wide" (https://supabase.com/docs/guides/auth/rate-limits) —
**사용자 1명당이 아니라 프로젝트 전체 합산**이다.

**그래서 왜 접었나**: 여러 사용자가 비슷한 시간대에 가입하면 3번째 요청부터
`429 email rate limit exceeded` 로 막힌다. 솔로 테스트 단계에서는 드러나지 않지만, 실제로
배포해서 여러 사람이 쓰게 하려면 **커스텀 SMTP 공급자(Resend·SendGrid 등) 연결이 옵션이 아니라
사실상 필수**가 된다. 그럴 거면 계정·DB를 낀 Supabase 계층을 유지할 이유가 약해진다 —
어차피 SMTP를 직접 붙일 거라면 SMTP만 쓰는 쪽이 단순하고, "로컬 우선·외부 서버 없음"
원칙과도 맞는다. 그 판단이 계정·DB 없는 SMTP 릴레이(`manager-relay/`)로 이어졌다.

> 이 절의 원본은 폐기된 `feature/sync2-supabase` 브랜치(`0ed628b`)에만 있었다. 브랜치를
> 정리해도 근거가 남도록 여기로 옮겼다. 당시 함께 적었던 "커스텀 SMTP 연결" 후속 작업
> 체크리스트는 Supabase 자체를 안 쓰기로 하면서 무효가 되어 옮기지 않았다.
