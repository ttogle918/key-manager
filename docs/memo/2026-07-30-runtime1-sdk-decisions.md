# 결정 메모 — RUNTIME-1 런타임 키 주입 SDK 설계 (2026-07-30)

> 대상: `docs/BACKLOG.md`의 **RUNTIME-1(`keylens-env` — dotenv 대체 런타임 SDK)**.
> 목적: 왜 이렇게 설계했는지 이유를 남겨서, 착수 시점에 다시 헤매지 않게 한다.
> SYNC-2 결정 메모와 같은 형식 — 이것도 코드가 아니라 결정 기록이다.

## 배경

지금 KeyLens는 CORE-5로 `.env` 파일을 내보내 쓰는 게 전부다. 그런데 이건 결국 디스크에 평문 파일을 만드는 것과 같아서, 금고에 암호화해 둔 의미가 실행 순간 무너진다. `keylens-env`는 `dotenv`처럼 코드에서 한 줄로 값을 불러오되, 파일을 읽는 대신 **실행 중이고 잠금 해제된 KeyLens**에서 그때그때 값을 받아오는 방식으로 이 평문 파일 문제를 없앤다. 이 문서는 그 설계 과정에서 나온 5개 결정과 이유를 기록한다.

---

## 결정 1 — Python 우선, Node.js는 로드맵으로 미룸

**결정**: v1은 PyPI에 배포하는 Python 패키지(`python-dotenv`와 유사한 API)만 만든다. npm용 Node 패키지는 이번엔 만들지 않고 로드맵으로 남긴다.

**왜**:
- KeyLens 백엔드 자체가 Python(FastAPI)이라, 같은 언어로 SDK를 만들면 로컬 API 계약을 재사용하기 쉽고 구현이 빠르다.
- 둘 다 동시에 만들면 범위가 커져서 "설계만 확정, 착수는 나중"이라는 이번 결정의 취지(SYNC-2와 동일)에 안 맞는다. 하나를 제대로 만들고 나서 두 번째 언어로 넓히는 게 낫다.
- 트레이드오프로 인정한 것: dotenv 생태계 자체는 Node.js 쪽이 더 크지만, 이번 범위에서는 "빠르게 만들 수 있는 쪽"을 택했다.

---

## 결정 2 — SDK 단독 동작이 아니라 "KeyLens 실행+잠금 해제 필수"

**결정**: `keylens-env`는 자체 암호화·인증 로직을 두지 않는다. KeyLens 앱(로컬 백엔드)이 켜져 있고 잠금 해제된 상태에서만 동작하며, 그 상태가 아니면 명확한 에러를 던진다.

**왜**:
- SDK가 독립적으로 동작하려면 마스터 비밀번호를 다루는 암호화 코드를 SDK 안에도 또 만들어야 하고, 매번(또는 어딘가에) 비밀번호를 넣어야 하는 문제가 생긴다 — 결국 SYNC-2 때 "인증/데이터 분리" 결정과 같은 이유로, 복호화 로직은 한 곳(KeyLens 백엔드)에만 있는 게 안전하고 단순하다.
- 기존 VAULT-2의 "인증 후에만 값 조회" 원칙을 새로 만들지 않고 그대로 재사용할 수 있다 — 코드 재사용이자 보안 모델의 일관성.
- 조용히 실패하거나 빈 값을 반환하지 않고 명확한 에러를 던지는 이유: 이 프로젝트의 "정직함" 원칙(SECURITY_REVIEW.md에서 허위 보안 표시를 걷어낸 것과 같은 맥락) — 값을 못 가져왔는데 조용히 넘어가면 개발자가 빈 환경변수로 앱을 돌리다가 나중에 더 헷갈리는 방식으로 실패한다.

---

## 결정 3 — 디렉토리 허용 목록은 "프로젝트 그룹" 단위로 관리

**결정**: 접근 제어는 키(entry) 하나하나가 아니라, 기존 "프로젝트" 필드를 정식 그룹 단위로 승격해서 관리한다. 한 프로젝트에 묶인 여러 키(Notion+OpenAI+DB 등)를 한 번에 허용/등록한다.

**왜**:
- 실제 dotenv 사용 패턴 자체가 "한 레포가 여러 개의 키를 한 번에 쓴다"이다. 키 단위로 허용을 관리하면 프로젝트 하나 등록에 설정이 여러 번 필요해 번거롭다.
- 이미 항목에 "프로젝트" 텍스트 필드가 있었으니 새 개념을 추가하는 대신 기존 필드를 승격하는 쪽이 구현·개념 모두 더 단순하다.

---

## 결정 4 — 프로젝트 미지정 키는 전역, 충돌 시 프로젝트가 우선

**결정**: 프로젝트가 지정되지 않은("기본") 키는 모든 프로젝트에서 접근 가능하다. 같은 환경변수명이 기본 키와 특정 프로젝트 키 양쪽에 있으면 프로젝트 쪽이 우선(override)하고, 이름이 겹치지 않으면 둘 다(기본+프로젝트) 합쳐서 내려준다.

**왜** (사용자 원문 근거):
- 모든 키에 일일이 프로젝트를 지정하게 만들면 "그냥 개인적으로 쓰는 키"(어느 프로젝트에도 속하지 않는 범용 키)까지 강제로 프로젝트에 묶이게 되어 불편하다. 프로젝트를 안 정한 키는 기본값으로 어디서든 쓸 수 있게 하는 게 자연스럽다.
- 셸 프로필(전역 설정) vs 로컬 `.env`(프로젝트 오버라이드)와 같은 이미 익숙한 우선순위 모델이라, 프로젝트 쪽이 이기는 규칙이 직관적이다.
- 이름이 안 겹치면 합쳐서 내려주는 이유: 굳이 막을 이유가 없다 — 프로젝트 전용 키 + 전역 키를 동시에 쓰는 게 일반적인 사용 패턴이다.

---

## 결정 5 — 디렉토리 등록: 사전 등록 + 미등록 요청 시 승인 프롬프트

**결정**: 설정 화면에서 허용 디렉토리를 미리 등록할 수도 있고, 등록 안 된 경로가 처음 요청하면 KeyLens 창에 "이 경로가 이 프로젝트 키를 요청함 — 허용?" 팝업이 뜬다. 허용하면 그 경로가 등록되어 이후 자동 통과한다.

**왜**:
- 사전 등록만 강제하면, 새 레포를 만들 때마다 먼저 KeyLens를 열어 설정에 가서 경로를 입력해야 하는 번거로움이 있다. 승인 프롬프트를 추가하면 "그냥 `load_env()`를 호출하고, 뜨는 팝업에서 허용을 누르는" 흐름이 되어 마찰이 준다.
- KeyLens가 이미 "실행 중이고 잠금 해제된 상태"라는 전제(결정 2)가 있기 때문에, 사용자가 바로 그 자리에서 팝업에 응답할 수 있다는 게 보장된다 — OAuth 동의창·SSH 에이전트 포워딩과 같은, 이미 검증된 UX 패턴을 그대로 가져올 수 있다.
- 사전 등록도 함께 남겨둔 이유: CI/무인 환경처럼 승인 팝업에 응답할 사람이 없는 상황을 위한 대비책.

---

## 결정 6 — 승인 요청 알림은 실행 형태별로 다른 채널을 쓴다

**결정**: 승인 대기 요청을 사용자가 놓치지 않도록, **데스크톱 앱(exe)**에서는 OS 네이티브 토스트(`plyer`, MIT) + Windows `FlashWindowEx`(표준 라이브러리 `ctypes`, 새 의존성 없음)로 작업표시줄을 깜빡인다. **브라우저 개발 모드**(`npm run dev`)에서는 OS 알림을 만들 수 없으므로 브라우저 `Notification` Web API로 대체하되, 화면 안 배너를 항상 병행해 최후 안전망으로 둔다.

**왜**:
- 데스크톱 앱과 브라우저 탭은 OS 차원에서 가능한 일 자체가 다르다 — pywebview로 감싼 데스크톱 앱은 Python 프로세스라 OS 알림 API를 직접 부를 수 있지만, 브라우저 탭은 샌드박스 안에 있어서 매번 권한을 물어야 하고 탭이 백그라운드일 때 신뢰도가 떨어진다. 이 차이를 숨기지 않고 각 채널에 맞는 방법을 쓰기로 했다.
- 실제 배포 형태는 데스크톱 exe(OSS-3 데스크톱 패키징에서 이미 완료)를 전제로 하므로, 여기에 진짜 알림 경험(토스트+작업표시줄 깜빡임)을 투자하는 게 맞다. 브라우저 알림은 어디까지나 개발 중에 쓰는 대체 수단이라는 점을 문서에 명시하기로 했다 — "웹 버전에서도 완벽히 동작한다"처럼 과장하지 않는다(이 프로젝트의 정직함 원칙).
- Windows 작업표시줄 깜빡임에 새 의존성을 추가하지 않은 이유: `ctypes`는 표준 라이브러리라 라이선스 검토·의존성 추가 없이 바로 쓸 수 있다. macOS(dock 바운스)·Linux(urgency hint)는 각각 플랫폼별 API가 달라 1차 범위에서는 Windows만 우선하고 후속으로 남겼다.

---

## 보안 프레이밍 — 새 신뢰 경계가 아니라 최소 권한 스코핑

이 기능은 KeyLens에 새로운 공격 표면을 추가하는 게 아니다. 잠금 해제 상태에서는 이미 같은 기기의 로컬 프로세스가 vault API를 호출해 값을 가져갈 수 있었다(기존 위협모델 그대로 — "이미 장악된 호스트는 방어 범위 밖"). RUNTIME-1이 실제로 바꾸는 것은, 지금은 인증만 되면 "전부 다" 보이던 것을 **승인된 프로젝트 것만** 보이게 좁히는 것이다. 착수 시 README/위협모델 문서에 이 점을 반드시 명시할 것 — 신뢰 경계를 새로 만든 것처럼 오해하게 두지 않는다.
